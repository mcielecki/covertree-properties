# Covertree Properties — Specification

Single source of truth for implementation. Derived from [REQUIREMENTS.md](REQUIREMENTS.md)
and [CLAUDE.md](../CLAUDE.md). If code and this document disagree, one of them is a bug:
fix the code or update this spec in the same change.

Library APIs referenced here were checked with context7 on 2026-09-26
(GraphQL Yoga, GraphQL Code Generator server + client presets, Prisma ORM 7).

## 0. Decisions summary

| # | Topic | Decision |
|---|---|---|
| 1 | City filter | Case-insensitive **exact** match: plain equality on an indexed `cityKey` column (normalized, lowercase) |
| 2 | Filter combination | Fields combined with AND; one value per field |
| 3 | Sorting | `sortOrder: SortOrder = DESC` on `createdAt`; tiebreaker `id` (same direction) |
| 4 | Pagination | Offset: `limit` (default 20, max 100), `offset` (default 0); returns `{ items, totalCount }` |
| 5 | ID | UUID generated by Postgres (`gen_random_uuid()`), exposed as `ID!` |
| 6 | Missing property | `property(id)` → `null`; `deleteProperty` on missing id → `NOT_FOUND` |
| 7 | Delete | Hard delete; `deleteProperty(id: ID!): ID!` returns the deleted id |
| 8 | Update | Out of scope; no `updatedAt` |
| 9 | Duplicates | Rejected with `ALREADY_EXISTS`; checked **before** calling Weatherstack |
| 10 | `USState` | 50 states + DC |
| 11 | Input normalization | Trim, collapse inner whitespace, keep casing; street 1–200, city 1–100; zip is a 5-digit string |
| 12 | Weatherstack `query` | `"{zipCode}"` |
| 13 | Resolved location check | Reject if `location.country` is not the United States |
| 14 | Units | Fahrenheit, fixed (`units=f`). No units column, no env switch |
| 15 | Weather failure | Mutation fails, nothing persisted |
| 16 | Timeout / retry | 5 s timeout (`AbortSignal.timeout`), no retries |
| 17 | Base URL | `WEATHERSTACK_BASE_URL`, default `https://api.weatherstack.com` |
| 18 | `weatherData` | Raw `current` stored as JSON; exposed as typed `WeatherData` GraphQL object; zod-validated on ingress (only 4 fields required, rest optional/nullable) |
| 19 | Field names | `lat`, `long` (`Float!`) as in requirements; `createdAt: DateTime!` |
| 20 | Web pages | `/`, `/properties/new`, `/properties/:id`; filters/sort/page in URL; delete with confirm |
| 21 | State input | `<select>` from generated `USState` enum; client-side zod mirrors API rules |
| 22 | Test DBs | `covertree_test` (integration) and `covertree_e2e` (Playwright), both in the same Postgres container |
| 23 | Adapter tests | Fixture-based, mocked `fetch`; no live calls in any test |
| 24 | E2E | One Playwright smoke flow with the fake weather provider |
| 25 | Running | `docker compose up` = db + api + web; dev mode = compose runs only `db`, apps via `pnpm dev` |

## 1. Acceptance criteria

Notation: **G** = Given, **W** = When, **T** = Then. "Valid input" means
`{ street: "15528 E Golden Eagle Blvd", city: "Fountain Hills", state: AZ, zipCode: "85268" }`
unless stated otherwise. In API tests the weather provider is a fake unless stated otherwise.

### US-1 — Query all properties
- **AC-1.1** G no properties, W `properties` is queried without arguments,
  T it returns `{ items: [], totalCount: 0 }`.
- **AC-1.2** G 3 properties, W `properties` is queried without arguments,
  T `items` has 3 entries and `totalCount` is 3.
- **AC-1.3** G 25 properties, W `properties` is queried without arguments,
  T `items` has 20 entries (default limit) and `totalCount` is 25.
- **AC-1.4** G 25 properties, W `properties(limit: 10, offset: 20)`,
  T `items` has 5 entries and `totalCount` is 25.
- **AC-1.5** G any data, W `limit` < 1, `limit` > 100 or `offset` < 0,
  T the response has a `BAD_USER_INPUT` error and `data` is `null`.
- **AC-1.6** G properties exist, W `properties` is queried, T **no** request is made to Weatherstack
  (asserted by a fake provider that records calls, and by a spy on `fetch` in the integration suite).

### US-2 — Sort by creation date
- **AC-2.1** G properties A, B, C created in that order, W `properties` is queried without `sortOrder`,
  T items come back as C, B, A (newest first).
- **AC-2.2** G the same data, W `properties(sortOrder: ASC)`, T items come back as A, B, C.
- **AC-2.3** G two properties with identical `createdAt`, W queried twice with the same arguments,
  T the order is identical in both responses (tiebreak on `id`).
- **AC-2.4** G sorting and a filter are both supplied, T the filter is applied first,
  then sorting, then pagination. `totalCount` reflects the filtered set.

### US-3 — Filter by city, zip code and state
- **AC-3.1** G properties in "Fountain Hills" and "Phoenix", W `filter: { city: "fountain hills" }`,
  T only the Fountain Hills properties are returned.
- **AC-3.2** G a property in "Fountain Hills", W `filter: { city: "Fountain" }`,
  T nothing is returned (exact match, not contains).
- **AC-3.3** G `filter: { city: "  Fountain   Hills " }`, T it behaves exactly like `"Fountain Hills"`.
- **AC-3.4** G properties in zips 85268 and 85001, W `filter: { zipCode: "85268" }`,
  T only the 85268 properties are returned.
- **AC-3.5** G properties in AZ and CA, W `filter: { state: AZ }`, T only AZ properties are returned.
- **AC-3.6** G `filter: { city: "Phoenix", state: AZ }`, T only properties matching **both** are returned.
- **AC-3.7** G `filter: { zipCode: "852" }` or a city that fails the city rules (§2.3),
  T a `BAD_USER_INPUT` error is returned.
- **AC-3.8** G `filter: { state: XX }`, T GraphQL validation fails (`GRAPHQL_VALIDATION_FAILED`).
- **AC-3.9** G a filter field is omitted or `null`, T that field does not constrain the result.

### US-4 — Property details
- **AC-4.1** G an existing property, W `property(id)` is queried,
  T all fields are returned: `id, street, city, state, zipCode, lat, long, weatherData, createdAt`.
- **AC-4.2** G a well-formed UUID that does not exist, W `property(id)`, T `data.property` is `null`
  and there are no errors.
- **AC-4.3** G an id that is not a UUID, W `property(id)`, T a `BAD_USER_INPUT` error is returned.
- **AC-4.4** W `property(id)` is queried, T no request is made to Weatherstack.
- **AC-4.5** `weatherData` returns the values stored at creation time. They are never refreshed.

### US-5 — Add a property
- **AC-5.1** G valid input and Weatherstack returns a valid US response, W `createProperty`,
  T a property is persisted and returned with a UUID `id`, the normalized input fields,
  `lat`/`long` parsed from `location.lat` / `location.lon` as numbers,
  `weatherData` equal to the response's `current` object, and `createdAt` ≈ now.
- **AC-5.2** W `createProperty` succeeds, T exactly **one** Weatherstack request is made, with
  `query=<zipCode>` and `units=f`.
- **AC-5.3** G `zipCode` is not exactly 5 digits (`"8526"`, `"852680"`, `"8526a"`, `"85268-1234"`),
  T `BAD_USER_INPUT`, nothing persisted, Weatherstack not called.
- **AC-5.4** G `street` or `city` is empty or whitespace-only, or longer than its limit,
  T `BAD_USER_INPUT`, nothing persisted, Weatherstack not called.
- **AC-5.5** G `state` is not a `USState` value, T `GRAPHQL_VALIDATION_FAILED`, Weatherstack not called.
- **AC-5.6** G input `{ street: "  15528  E Golden Eagle Blvd ", city: " Fountain  Hills" … }`,
  T the stored values are `"15528 E Golden Eagle Blvd"` and `"Fountain Hills"`.
- **AC-5.7** G a property with the same normalized address exists (case-insensitive on street and city),
  W `createProperty`, T `ALREADY_EXISTS`, Weatherstack **not** called, nothing persisted.
- **AC-5.8** G Weatherstack returns HTTP 200 with `success: false, error.code: 615`,
  T `LOCATION_NOT_FOUND`, nothing persisted.
- **AC-5.9** G Weatherstack returns a location whose `country` is not the US, T `LOCATION_NOT_FOUND`,
  nothing persisted.
- **AC-5.10** G Weatherstack returns any other `success: false` error (e.g. 101, 104, 105),
  a non-2xx status, a non-JSON body, a body without a usable `location` (lat/lon/country),
  or a `current` object missing a **required** field (`observation_time`, `temperature`,
  `weather_descriptions`, `weather_icons`) or with a wrong type in one of them,
  T `WEATHER_SERVICE_UNAVAILABLE`, nothing persisted. The provider's error code is logged server-side,
  not exposed to the client.
- **AC-5.11** G Weatherstack does not answer within `WEATHERSTACK_TIMEOUT_MS` (default 5000),
  T `WEATHER_SERVICE_UNAVAILABLE` within timeout + a small margin. Nothing persisted. No retry.
- **AC-5.12** G two concurrent `createProperty` calls with the same address,
  T exactly one succeeds and the other fails with `ALREADY_EXISTS` (unique constraint backstop).
- **AC-5.13** The API key never appears in responses, logs or error messages.
- **AC-5.14** G a valid US response whose `current` lacks any non-required field (e.g. `uv_index`,
  `is_day`, `wind_degree`) or has one with an unexpected type, W `createProperty`,
  T the property is created. Each missing field resolves to `null` in `weatherData`, and a field
  with a wrong type is dropped from the stored object and also resolves to `null`.

### US-6 — Delete a property
- **AC-6.1** G an existing property, W `deleteProperty(id)`, T it returns the same `id`,
  and a subsequent `property(id)` returns `null`.
- **AC-6.2** G a well-formed UUID that does not exist, W `deleteProperty(id)`, T `NOT_FOUND`.
- **AC-6.3** G a malformed id, W `deleteProperty(id)`, T `BAD_USER_INPUT`.
- **AC-6.4** G a deleted property, W the same address is created again, T it succeeds (hard delete).

### US-7 — Property fields
- **AC-7.1** The `Property` type exposes exactly: `id: ID!, street: String!, city: String!,
  state: USState!, zipCode: String!, lat: Float!, long: Float!, weatherData: WeatherData!,
  createdAt: DateTime!`.
- **AC-7.2** `id` and `createdAt` are generated server/DB-side. They cannot be supplied by the client.
- **AC-7.3** `lat`/`long` come only from the Weatherstack response, never from client input.

### Web
- **AC-W.1** `/` lists properties (street, city, state, zip, current temperature °F, created date), sorted newest first.
- **AC-W.2** The filter controls (city text, state select, zip text) and the sort toggle update the URL query string
  (`?city=&state=&zip=&sort=asc|desc&page=`). Reloading the page restores the same view.
- **AC-W.3** Pagination controls show "page X of Y" based on `totalCount`. Changing a filter resets to page 1.
- **AC-W.4** `/properties/new` validates on the client with the same rules as the API. Invalid fields show inline messages
  and the request is not sent. API errors are shown in human terms per error code (§5).
  On success it navigates to `/properties/:id`.
- **AC-W.5** `/properties/:id` shows all fields plus a weather card (icon, description, temperature °F, feels-like,
  wind mph + direction, humidity %, observation time labelled as UTC, e.g. "Observed 12:14 PM UTC").
  Nullable weather fields that are `null` are hidden, never shown as "null" or 0. An unknown id shows a
  "Property not found" state.
- **AC-W.6** Delete is available on the list and details pages. It asks for confirmation.
  After `createProperty` or `deleteProperty` succeeds, the active `Properties` list query is refetched
  (`refetchQueries`), so the list is correct without a full reload. On the details page, a successful
  delete evicts the `Property` entity from the Apollo cache (`cache.evict` + `cache.gc`) and redirects to `/`.
- **AC-W.7** Loading and error states are shown for every query and mutation.

## 2. GraphQL API

### 2.1 SDL

Split into modules for the Codegen server preset (§6). Shown here as one document.

```graphql
# ---------- base ----------
scalar DateTime   # graphql-scalars DateTimeResolver; ISO-8601 string on the wire

enum SortOrder {
  ASC
  DESC
}

type Query
type Mutation

# ---------- property ----------
"""
Two-letter USPS abbreviations: the 50 states and the District of Columbia.
"""
enum USState {
  AL AK AZ AR CA CO CT DE DC FL GA HI ID IL IN IA KS KY LA ME MD MA MI MN MS MO
  MT NE NV NH NJ NM NY NC ND OH OK OR PA RI SC SD TN TX UT VT VA WA WV WI WY
}

type Property {
  id: ID!
  "Street name and number, e.g. '15528 E Golden Eagle Blvd'."
  street: String!
  city: String!
  state: USState!
  "Exactly 5 digits. A string, so leading zeros are preserved."
  zipCode: String!
  "Latitude of the location Weatherstack resolved for the zip code."
  lat: Float!
  "Longitude of the location Weatherstack resolved for the zip code."
  long: Float!
  "Weather observed when the property was created. Never refreshed."
  weatherData: WeatherData!
  createdAt: DateTime!
}

"""
Weatherstack `current` object, units = Fahrenheit ('f'):
temperature/feelsLike in °F, windSpeed in mph, pressure in mb,
precip in inches, visibility in miles.
Only the first four fields are guaranteed; the rest are null when Weatherstack omits them.
"""
type WeatherData {
  "Time of observation in UTC, as returned by Weatherstack, e.g. '12:14 PM'."
  observationTime: String!
  temperature: Float!
  weatherDescriptions: [String!]!
  weatherIcons: [String!]!
  feelsLike: Float
  weatherCode: Int
  windSpeed: Float
  windDegree: Int
  windDir: String
  pressure: Float
  precip: Float
  humidity: Int
  cloudCover: Int
  uvIndex: Float
  visibility: Float
  isDay: Boolean
}

input PropertyFilter {
  "Case-insensitive exact match."
  city: String
  "Exactly 5 digits."
  zipCode: String
  state: USState
}

type PropertyPage {
  items: [Property!]!
  "Total number of properties matching the filter, ignoring limit/offset."
  totalCount: Int!
}

input CreatePropertyInput {
  street: String!
  city: String!
  state: USState!
  zipCode: String!
}

extend type Query {
  properties(
    filter: PropertyFilter
    sortOrder: SortOrder = DESC
    "1..100"
    limit: Int = 20
    ">= 0"
    offset: Int = 0
  ): PropertyPage!

  "Returns null if no property has this id."
  property(id: ID!): Property
}

extend type Mutation {
  """
  Creates a property. Calls Weatherstack once to fetch current weather and coordinates.
  Fails without persisting anything if the weather lookup fails.
  """
  createProperty(input: CreatePropertyInput!): Property!

  "Hard-deletes a property. Returns its id. Fails with NOT_FOUND if it does not exist."
  deleteProperty(id: ID!): ID!
}
```

### 2.2 Rationale for non-obvious choices

- **`PropertyPage { items, totalCount }` rather than a Relay connection.** The UI needs "page X of Y",
  and offset pagination gives that directly. Cursor connections add `edges`/`pageInfo` boilerplate
  that nothing here needs.
- **`sortOrder` argument rather than an `orderBy` input.** Creation date is the only sort key in the
  requirements. A general `orderBy` input would add a field enum with one value.
- **`property(id)` is nullable and returns `null`.** This is the usual GraphQL convention for lookups.
  `deleteProperty` raises `NOT_FOUND` instead, because the client asked for a state change that could
  not happen.
- **`deleteProperty` returns `ID!`.** That is all Apollo needs for `cache.evict`. Returning the deleted
  object would imply the client can still read a record that no longer exists.
- **A typed `WeatherData` object rather than a `JSON` scalar.** Clients get a schema, codegen types
  and field selection. The database still stores the raw `current` object exactly as the
  requirements say. `WeatherData` resolvers map snake_case JSON to camelCase fields using a Codegen
  mapper. Paid-plan extras such as `astro` and `air_quality` are kept in the stored JSON but
  not exposed.
- **Only four `WeatherData` fields are non-null.** The weather card cannot work without
  `observationTime`, `temperature`, `weatherDescriptions` and `weatherIcons`. The other fields are
  cosmetic. If Weatherstack drops or renames one of them, property creation must not break, so
  they are nullable and the UI hides them when they are null.
- **Numeric measurements use `Float`, while codes and percentages use `Int`.** Weatherstack returns
  integers today. `Float` keeps serialization from breaking if it starts returning decimals.
- **`zipCode` is a `String`.** Leading zeros (`02134`) must survive.
- **No custom `ZipCode` / `UUID` scalars.** Validation lives in one place, the zod schemas in the
  service layer (§2.3), so every rule produces the same `BAD_USER_INPUT` shape. GraphQL-level
  scalars would split the rules and produce a different error code.
- **`lat` / `long` field names** are taken from the requirements, even though `long` reads oddly in
  TypeScript.

### 2.3 Input validation (zod, service layer)

| Field | Rule (applied after normalization) |
|---|---|
| normalization | `trim()`, then collapse runs of whitespace to one space. Casing is kept. |
| `street` | 1–200 chars, no control characters |
| `city` | 1–100 chars, matches `^[\p{L}][\p{L} .'-]*$` (Unicode letters, space, `.`, `'`, `-`) |
| `zipCode` | `^\d{5}$` |
| `state` | enforced by the GraphQL enum; zod re-checks it as `z.enum(US_STATES)` for defense in depth |
| `id` args | `z.uuid()` (RFC 9562; zod 4 deprecates `z.string().uuid()`) |
| `limit` | integer, 1–100; explicit `null` → default 20 |
| `offset` | integer, ≥ 0; explicit `null` → default 0 |

The same rules apply to `PropertyFilter.city` and `PropertyFilter.zipCode`. A `null` or omitted
filter field means no constraint (AC-3.9). An empty or whitespace-only filter value fails the
1-char rule and is `BAD_USER_INPUT`, so the web client omits empty inputs. GraphQL applies
argument defaults only when an argument is omitted, which is why `null` for `limit`/`offset` is
mapped to the default by the schema. Validation messages are human-readable (e.g. "Zip code must
be exactly 5 digits"), one per field, because the web form shows them inline and the API returns
them in `fieldErrors`.

**Case-insensitive city filter.** One pure function, `toCityKey(city)`, normalizes a city and
lowercases it. It runs both when a property is written (stored in `cityKey`) and on
`PropertyFilter.city`. The repository then filters with plain equality (`where: { cityKey }`) on an
indexed column. There is no `ILIKE` and no Prisma `mode: 'insensitive'`.

The rules live in a shared module (`packages/validation`) so the web form uses exactly the same
schemas (§6).

## 3. Data model (Prisma 7)

```prisma
// apps/api/prisma/schema.prisma
generator client {
  provider = "prisma-client"
  output   = "../src/generated/prisma"
}

datasource db {
  provider = "postgresql"
  // URL lives in prisma.config.ts (Prisma 7).
}

enum USState {
  AL
  AK
  // ... one value per line (Prisma syntax), same 51 values as the GraphQL USState
  WY
}

model Property {
  id          String   @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  street      String   @db.VarChar(200)
  city        String   @db.VarChar(100)
  /// toCityKey(city): normalized lowercase city; used for case-insensitive equality filtering.
  cityKey     String   @map("city_key") @db.VarChar(100)
  state       USState
  zipCode     String   @map("zip_code") @db.Char(5)
  /// Normalized lowercase "street|city|state|zip"; enforces uniqueness of addresses.
  addressKey  String   @unique @map("address_key")
  lat         Float
  long        Float
  /// Raw Weatherstack `current` object (units=f).
  weatherData Json     @map("weather_data")
  createdAt   DateTime @default(now()) @map("created_at") @db.Timestamptz(3)

  @@index([createdAt, id])
  @@index([cityKey])
  @@index([state])
  @@index([zipCode])
  @@map("properties")
}
```

Notes:
- **Prisma 7 specifics** (verified): the `prisma-client` generator requires an explicit `output`. The
  datasource URL moves to `prisma.config.ts` (`defineConfig({ schema, migrations, datasource: { url } })`),
  which must `import 'dotenv/config'` because Prisma 7 no longer loads `.env` itself. The runtime
  client uses the driver adapter `@prisma/adapter-pg` (`new PrismaPg({ connectionString })`).
- **Version pin:** `prisma` is pinned to `7.10.0`. At implementation time its npm `latest` tag
  pointed at an 8.0 release candidate, while `@prisma/client` and `@prisma/adapter-pg` were on
  7.10.0. `prisma.config.ts` reads `DATABASE_URL` with `process.env`, not `env()`, because `env()`
  throws when the variable is unset and `prisma generate` (run on `postinstall`) must work
  without a database.
- **`gen_random_uuid()`** is built into Postgres 13 and later, so the database generates the id as
  the requirements ask.
- **`addressKey` and `cityKey` instead of expression indexes.** Prisma's schema cannot express
  `UNIQUE (lower(street), …)` or `INDEX (lower(city))`. Computed columns keep the rules visible in
  the schema, portable and indexable with plain equality. The service computes them with pure
  functions, `toAddressKey()` and `toCityKey()`, each with its own unit tests. Neither column is
  exposed in GraphQL.
- **Enums line up across layers.** The GraphQL `USState`, the Prisma `USState` and the zod `US_STATES`
  all use the same string values. Codegen runs with `enumsAsTypes: true`, so a GraphQL `USState` is a
  string union that fits Prisma's enum without mapping code.
- **`lat` / `long` use `Float` (`double precision`).** Weatherstack returns 3 decimal places, so
  `Decimal` would add conversion code for no gain.
- Migrations are committed in `apps/api/prisma/migrations`. The api container runs `prisma migrate deploy` when it starts.

## 4. Weatherstack integration

### 4.1 Port

```ts
// apps/api/src/weather/weather-provider.ts — plain TypeScript, no zod, no adapter imports
export interface WeatherCurrent {
  observation_time: string;
  temperature: number;
  weather_descriptions: string[];
  weather_icons: string[];
  feelslike?: number;               // ...the other optional fields of §4.3
  is_day?: 'yes' | 'no';
  [key: string]: unknown;           // unmodelled extras (astro, air_quality, ...)
}

export interface WeatherLookup {
  lat: number;
  long: number;
  current: WeatherCurrent;
}

export interface WeatherProvider {
  /** Throws LocationNotFoundError | WeatherUnavailableError. */
  getCurrentByZip(zipCode: string): Promise<WeatherLookup>;
}
```

**Dependency direction.** The port owns the domain types. Adapters import from it, and it imports
nothing from `weather/weatherstack/`. The adapter's zod schema is declared
`weatherCurrentSchema = z.looseObject({...}) satisfies z.ZodType<WeatherCurrent>`, so a schema
whose output drifts from the domain type fails `tsc`.

Implementations:
- `WeatherstackProvider`, the real adapter.
- `FakeWeatherProvider`, a deterministic stand-in. It returns fixture data for any zip, can be set up
  to throw or delay, and records its calls. It is used by the API integration tests and the E2E flow,
  and can be selected at runtime with `WEATHER_PROVIDER=fake`. When that happens, `main.ts` logs a
  prominent `warn` line at startup, e.g.
  `WEATHER_PROVIDER=fake: weather data and coordinates are FAKE, Weatherstack will not be called`.

`PropertyService` receives the provider through its constructor. Only `PropertyService.create` ever calls it.

### 4.2 Request

```
GET {WEATHERSTACK_BASE_URL}/current?access_key={WEATHERSTACK_API_KEY}&query={zipCode}&units=f
```

- `WEATHERSTACK_BASE_URL` defaults to `https://api.weatherstack.com`. Some Weatherstack plans reject
  HTTPS with error `105 https_access_restricted`. The README tells reviewers on such a plan to set
  `WEATHERSTACK_BASE_URL=http://api.weatherstack.com`.
- The URL is built with `new URL()` and `URLSearchParams`, never by joining strings.
- The request uses global `fetch` with `signal: AbortSignal.timeout(WEATHERSTACK_TIMEOUT_MS)`
  (default 5000) and makes no retries.
- **The key is kept secret.** The full URL is never logged. Log lines contain only `zipCode`, the
  duration, the HTTP status and the Weatherstack error code/type.
- `query` is the zip code alone. Weatherstack treats a 5-digit value as a US ZIP. The coordinates
  returned are for the location Weatherstack resolved (roughly the ZIP's town), **not** the exact
  street address. The README and the `lat`/`long` field descriptions say so.

### 4.3 Response validation (zod)

Success body (the fields we rely on):

```jsonc
{
  "request":  { "type": "Zipcode", "query": "85268", "unit": "f", ... },
  "location": { "name": "Fountain Hills", "country": "United States of America",
                "region": "Arizona", "lat": "33.609", "lon": "-111.729", ... },
  "current":  { "observation_time": "12:14 PM", "temperature": 95, "weather_code": 113,
                "weather_icons": ["https://..."], "weather_descriptions": ["Sunny"],
                "wind_speed": 8, "wind_degree": 250, "wind_dir": "WSW", "pressure": 1010,
                "precip": 0, "humidity": 12, "cloudcover": 0, "feelslike": 93,
                "uv_index": 9, "visibility": 10, "is_day": "yes", ... }
}
```

Error body (**HTTP 200**):

```json
{ "success": false, "error": { "code": 615, "type": "request_failed", "info": "..." } }
```

Parsing order:
1. A non-2xx status → `WeatherUnavailableError`.
2. A body that isn't JSON → `WeatherUnavailableError`.
3. The body matches `{ success: false, error: { code: number, type: string, info?: string } }`:
   code `615` → `LocationNotFoundError`, and any other code → `WeatherUnavailableError`.
   The code and type are logged.
4. The body is parsed with the success schema:
   - `location.lat` and `location.lon` are **strings**. They are coerced with `Number()`, must be
     finite, and must be within [-90, 90] and [-180, 180].
   - `location.country` must be one of `"United States of America"`, `"USA"` or `"United States"`.
     Otherwise → `LocationNotFoundError` ("resolved outside the US").
   - `current` must contain the **required** fields: `observation_time` (string),
     `temperature` (number), `weather_descriptions` (string[]) and `weather_icons` (string[]).
   - Every other exposed field (`feelslike`, `weather_code`, `wind_speed`, `wind_degree`, `wind_dir`,
     `pressure`, `precip`, `humidity`, `cloudcover`, `uv_index`, `visibility`, `is_day`) is
     **optional**, declared as `.optional().catch(undefined)`. If one is missing or has the wrong
     type it becomes `undefined` and never fails the parse. `is_day` must be `"yes"` or `"no"`.
   - The schema is a `z.looseObject()` (zod 4; `.passthrough()` is deprecated) so fields we
     don't model (e.g. `astro`, `air_quality`) are kept in the stored JSON.
   - If a required field fails or `location` is unusable → `WeatherUnavailableError`. The zod issues
     are logged, but not the body.
5. The adapter returns `{ lat, long, current }`. `current` is exactly the validated object, extras
   included. Fields dropped by `.catch` are omitted (zod returns them as `key: undefined`, so the
   adapter strips undefined keys). The `WeatherData` resolvers turn any absent
   optional field into `null`.

### 4.4 Error mapping

| Condition | Domain error | GraphQL code |
|---|---|---|
| `success:false`, code 615 (location not found) | `LocationNotFoundError` | `LOCATION_NOT_FOUND` |
| Resolved country is not the US | `LocationNotFoundError` | `LOCATION_NOT_FOUND` |
| `success:false`, any other code (101 invalid key, 102 inactive, 104 quota, 105 HTTPS restricted, 601 …) | `WeatherUnavailableError` | `WEATHER_SERVICE_UNAVAILABLE` |
| Timeout (`TimeoutError` / `AbortError`) | `WeatherUnavailableError` | `WEATHER_SERVICE_UNAVAILABLE` |
| Network error, non-2xx, non-JSON, unusable `location`, required `current` field missing or invalid | `WeatherUnavailableError` | `WEATHER_SERVICE_UNAVAILABLE` |
| Optional `current` field missing or invalid | — (not an error) | property created, field is `null` |

Configuration problems (101, 102, 105) are the operator's to fix, not the user's. The client gets
only the generic "weather service unavailable" message, and the server log says exactly what went wrong.

### 4.5 Create flow

```
resolver createProperty
  → PropertyService.create(input)
      1. validate + normalize input (zod)          → BAD_USER_INPUT
      2. addressKey = toAddressKey(normalized); cityKey = toCityKey(normalized.city)
      3. repository.findIdByAddressKey(addressKey) → ALREADY_EXISTS { id }   (no API call spent)
      4. weather.getCurrentByZip(zipCode)          → LOCATION_NOT_FOUND / WEATHER_SERVICE_UNAVAILABLE
      5. repository.create({...normalized, addressKey, cityKey, lat, long, weatherData: current})
           P2002 unique violation (race)           → ALREADY_EXISTS
      6. return Property
```

No database transaction spans the HTTP call. The unique constraint in step 5 is the real guarantee.
Step 3 is only an optimization that saves quota. It returns the existing id, so `ALREADY_EXISTS`
can carry it (§5). After a race in step 5 the id is not known and is omitted.

## 5. Error model

All errors go in the standard GraphQL `errors[]` array with `extensions.code`. The service and
adapter layers throw **domain errors**, which are plain classes that know nothing about GraphQL.
One `maskError` function passed to Yoga (`createYoga({ maskedErrors: { maskError } })`) turns them
into `GraphQLError`s. Everything else goes through Yoga's default masking ("Unexpected error.").
Resolvers do not catch errors.

| `extensions.code` | Raised when | Message (client-facing) | Extra extensions |
|---|---|---|---|
| `GRAPHQL_VALIDATION_FAILED` | Invalid document or variables, e.g. an unknown `USState` value (Yoga/graphql-js, HTTP 400) | graphql-js message | — |
| `BAD_USER_INPUT` | zod validation fails (input, filter, id, limit/offset) | `"Invalid input"` | `fieldErrors: { [path]: string[] }` |
| `NOT_FOUND` | `deleteProperty` on an unknown id | `"Property not found"` | `id` |
| `ALREADY_EXISTS` | Same normalized address already stored | `"A property with this address already exists"` | `id` of the existing property, when known |
| `LOCATION_NOT_FOUND` | Weatherstack cannot resolve the zip, or resolves outside the US | `"Could not resolve a US location for zip code {zip}"` | `zipCode` |
| `WEATHER_SERVICE_UNAVAILABLE` | Timeout, network, quota, auth, HTTPS restriction, bad response | `"Weather service is unavailable, please try again later"` | — |
| `INTERNAL_SERVER_ERROR` | Anything unexpected (masked by Yoga) | `"Unexpected error."` | Only in dev: `originalError` |

- `fieldErrors` keys are the zod issue path relative to the validated argument: `street`, `city`,
  `state`, `zipCode` for `createProperty` input and for `PropertyFilter`, `limit` / `offset`, and
  `id`. Each field carries exactly one message (the first failing rule).
- HTTP status: Yoga's defaults apply. Execution errors return 200 with `errors[]` (as in the
  GraphQL-over-HTTP spec), and parse/validation errors return 400. Domain errors do not set
  `extensions.http`.
- A mutation that fails returns `data: null`, because `createProperty` and `deleteProperty` are
  non-null fields.
- The web client switches on `extensions.code` only, never on message text.
- Unexpected errors are logged with the operation name. PII is limited to the address, which is not sensitive here.

Layering rules (from CLAUDE.md), made concrete:
- **Resolvers** (`schema/**/resolvers`) only read args, call `context.propertyService.*` and return.
  They contain no Prisma, zod or `try/catch`. The exception is the `WeatherData` field resolvers, which
  are pure field mapping.
- **The service** (`property.service.ts`) validates input, normalizes it, checks for duplicates, calls
  the weather provider and the repository, and throws domain errors. It depends only on the
  `PropertyRepository` and `WeatherProvider` interfaces.
- **The repository** (`prisma-property.repository.ts`) is the only file that imports the Prisma
  client. It filters the city with equality on `cityKey`. It turns P2002 into `AlreadyExistsError`,
  and P2025 on delete into `NotFoundError`.
- **`app.ts`** wires everything through `createApp({ propertyService })`. `main.ts` builds the real
  dependencies and tests build them with fakes. No DI container is used, because constructor
  injection is enough.

**Web typed operations.** The Codegen docs now recommend the client preset over the older
`typescript-react-apollo` hooks plugin. Operations are written with the generated `graphql()`
function and passed to Apollo's own `useQuery` / `useMutation`. The result is fully typed "generated
typed hooks" without a second code generator. Apollo Client 4 exposes the React hooks from
`@apollo/client/react`; check with context7 at implementation time.

**Web cache strategy.** The cache is kept simple on purpose: the default `InMemoryCache` with no
custom `typePolicies` or manual list merging.
- `createProperty` and `deleteProperty` pass `refetchQueries: [PropertiesDocument]`, which refetches
  the active list query with its current variables (filters, sort order, page), and set
  `awaitRefetchQueries: true`.
- On the details page, a successful delete calls
  `cache.evict({ id: cache.identify({ __typename: 'Property', id }) })` and then `cache.gc()`, and
  navigates to `/`.

## 7. Testing strategy

TDD for business logic: each service and adapter behavior starts as a failing test.
Every test maps back to an AC id where possible (`it('AC-5.7: rejects duplicate address before calling weather', …)`).

### 7.1 Unit tests (Vitest, no I/O)

| Subject | What | Fakes |
|---|---|---|

| `keys.ts` | `toAddressKey`: case and whitespace insensitivity, field order, separators. `toCityKey`: case and whitespace insensitivity, same result for stored value and filter input | — |

The weather provider is not called on validation failure. Weather errors propagate and nothing is persisted. | In-memory `PropertyRepository`, `FakeWeatherProvider` |
| `WeatherstackProvider` | URL shape (`query`, `units=f`, key param, base URL override). Success mapping (string → number lat/lon, passthrough of extras). Minimal `current` with only the 4 required fields succeeds (AC-5.14). An optional field with the wrong type is dropped without failing. A missing required field → unavailable. Each row of §4.4. ### 7.2 API integration tests (Vitest + real Postgres)

- `createApp()` is built with the real `PrismaPropertyRepository` against the `covertree_test`
  database and a `FakeWeatherProvider`. Requests go through `yoga.fetch`, with no network port.
- The integration project connects only to `TEST_DATABASE_URL` (from the environment, else the
  repo-root `.env`, else the compose default). It never reads `DATABASE_URL`. globalSetup refuses
  to run, with a clear error, unless the database name ends with `_test`.
- The schema is migrated once per run with `prisma migrate deploy` in globalSetup (`DATABASE_URL` is
  set to the test URL for that child process only). Not `migrate reset`: Prisma 7 refuses
  destructive migrate commands when an AI agent runs them, and `deploy` is enough on a database
  whose data the tests truncate anyway. If a committed migration is ever edited, reset
  `covertree_test` manually once. Tables are truncated before each test. Test files run serially
  (`fileParallelism: false`) because they share the database.
- `PrismaPropertyRepository` runs the same contract suite as the in-memory fake
  (`property.repository.contract.ts`), so the fake used by the service unit tests cannot drift.
- **Coverage:** the full GraphQL surface end to end. That means every AC in US-1…US-7, including
  error codes and shapes, the default and max limit, sort stability, case-insensitive city via `cityKey`,
  ALREADY_EXISTS from the unique constraint (AC-5.12, run with `Promise.all`), and that queries
  never touch the provider (AC-1.6, AC-4.4).

### 7.3 Web tests (Vitest + React Testing Library)

- Components and pages render under Apollo's `MockedProvider` (or `MockLink`) and a memory router.
- **Covered:** filter and sort changes update the URL and the query variables (AC-W.2, W.3). Form
  validation blocks submission and shows messages (W.4). Each API error code renders its message.
  The list shows loading, error and empty states. Create and delete mutations are issued with
  `refetchQueries` for the list query, and a delete on the details page evicts the entity and
  redirects (W.6). The weather card formats °F, mph and %, labels the observation time as UTC, and
  hides null optional fields (W.5).

### 7.4 E2E (Playwright, one smoke flow)

`e2e/property-smoke.spec.ts`: create a property → it appears at the top of the list → filter by its
city and it is still shown, filter by another state and it is gone → delete it with confirmation →
it is gone. The API runs with `WEATHER_PROVIDER=fake` against its own `covertree_e2e` database,
separate from `covertree_test`, so E2E and integration runs never truncate each other's data. That
database is migrated and truncated in Playwright's `globalSetup`. The test is deterministic and uses
no API quota. It runs with `pnpm test:e2e` and is not part of `pnpm test`.

| Dependency | Unit | Integration | E2E |
|---|---|---|---|
| Weatherstack | fake provider, or stubbed `fetch` for the adapter | fake provider | fake provider |
| Postgres | in-memory repository | real (`covertree_test`) | real (`covertree_e2e`) |
| GraphQL server | — | real, in-process (`yoga.fetch`) | real, HTTP |
| Browser | jsdom | — | Chromium |

No test ever calls the real Weatherstack API. A manual check against the live API
(`WEATHER_PROVIDER=weatherstack`) is listed in the README as a pre-delivery step.

### 7.6 Definition of done (per step)

Before a step counts as done, `pnpm typecheck && pnpm lint && pnpm test` must pass. `pnpm test:e2e`
must also pass before delivery.

## 8. Out of scope

- Authentication, authorization, users, multi-tenancy
- Updating properties (no `updateProperty`, no `updatedAt`)
- Soft delete, undo, audit log
- Refreshing weather after creation, historical or forecast weather, caching weather responses
- Retries or circuit breakers around Weatherstack
- Geocoding the exact street address; coordinates are those Weatherstack resolves for the ZIP
- Maps or other visualizations of coordinates
- Addresses outside the 50 states + DC (territories, military APO/FPO, ZIP+4)
- Verifying that street/city/state/zip are mutually consistent (only the country is checked)
- Filtering by multiple values per field, partial/fuzzy search, sorting by anything but `createdAt`
- Cursor pagination, subscriptions, real-time updates
- Rate limiting, query depth/complexity limits, persisted queries
- Internationalization; unit switching (always °F / mph / in / mi)
- Cloud deployment, CI/CD pipelines beyond running the scripts locally
